# 企业制度问答助手 · BM25 + LLM 的 RAG 实现

> 一个检索增强问答（RAG）学习项目，**检索器使用标准库、可离线验证**；完整问答需要模型 API：用纯标准库实现 BM25 检索，只把命中的制度片段送进大模型，并强制"无依据即拒答"。
>
> 解决的问题很具体：企业内部制度散在几十份文档里，员工问一句"年假怎么请"，要么翻文档，要么直接找人问。直接问大模型，它要么不知道、要么编。

## 演示入口

## 效果（实测）

**语料**：`policy_context.txt`，15,853 字节，2 份制度文档（员工手册 + 员工行为规范），含 **56 个二/三级标题条目**（14 个二级章节 + 42 个三级小节）。**56 是标题条目数，不是切块数**。**已脱敏**——公司名等敏感信息已替换，制度结构与条款内容保留。

**切块**：标题挂载 + 滑动窗口（320 字窗口 / 60 字重叠），当前版本产出 **52 个片段**。

**评测集**：40 题，按制度类别平均分布（考勤与请假 / 年休假 / 加班 / 试用期 / 薪酬与社保，每类 8 题）。对齐语料真实内容后保留 **31 题**，另外 9 题的参考事实在语料中不存在，显式移入 `deferred` 而非删除。

**指标**：`score2` 字面覆盖分（输入＝参考答案与已生成回答，k=6），可离线复算、不依赖任何模型调用。**不是检索召回率，也不是答案正确率**。历史实现曾采用 `0.6 × bigram 召回 + 0.4 × 数字召回` 的复合定义，记录见 `docs/METRICS.md`，属旧口径，数字不与现行口径横向比较。

| 维度 | k=3 | **k=6** |
|---|---|---|
| 整体 | 0.610 | **0.674** |
| 试用期 | — | 0.78 |
| 加班 | — | 0.72 |
| 考勤与请假 | — | 0.69 |
| 薪酬与社保 | — | 0.65 |
| 年休假 | — | **0.56（最弱）** |

**成本**：40 题全量跑一遍 < $0.01；三轮迭代（修复复算 → score2 实跑 → 检索优化重跑）合计 < $0.015。检索与离线复算零 Token。

**历史优化记录**：材料记载查询同义词扩展、标题挂载及薪酬与社保类 0.234 / 0.65 等数字。评分口径与实验条件尚未在本仓库形成完整可复现对照，因此不将这些数字解释为已验证的改进幅度，也不据此确认唯一根因。

> ⚠️ **口径说明（2026-11-05 修订）**：`0.674` 是**历史 31 题保存回答的 score2 字面覆盖分（k=6）**，输入为参考答案与已生成回答；**不是检索召回率、不是答案正确率**。`56` 是二/三级标题条目数，不是块数；当前切块 **52**。早期 `323→151` 是另一份更完整语料的快照，与当前 52 不可拼成同一结果。
> 本仓库 `docs/METRICS.md` 保留 2026-09/10 的实测记录与当时的定义，属**历史口径**；四个阶段的数字口径不同，不可横向比较。对外讲述一律使用上述定案口径。

## 架构

```
【索引期 · 离线 · 零 Token】
  policy_context.txt
      │  Markdown 标题层级解析
      ▼
  标题挂载切块（320 字窗口 / 60 字重叠）
      │  每个块携带章节路径，如「6.4.6 带薪年休假」
      ▼
  BM25 打分（每块词频字典 + 全局 IDF + 逐块扫描，**无倒排表**）→ 52 个片段

【查询期 · 在线 · 每次只送命中片段】
  用户问题
      │  查询同义词扩展（仅查询侧，不改索引与打分）
      ▼
  BM25 检索 Top-k
      ▼
  拼装 context，标注【政策片段 N】
      ▼
  DeepSeek 生成（temperature=0）
      │  system prompt 强制：只依据上下文、无依据即拒答、标注来源
      ▼
  答案 + 引用来源
```

**关键点：每次 API 调用只携带命中的 k 个片段**，而不是把整本手册塞进 prompt。这是本项目在成本上最重要的一处设计——制度手册塞满上下文不仅贵，还会稀释关键条款。

## 三个关键设计取舍

### 1. 为什么用 BM25，而不是向量检索

| 理由 | 说明 |
|---|---|
| 场景匹配 | 制度问答的提问用词与文档用词重合度高（问"年假"、文档写"带薪年休假"），关键词能对上；开放域问答才迫切需要语义泛化 |
| 零依赖 | 纯标准库，clone 下来就能跑。不需要 embedding 模型、不需要 API Key、不需要 GPU |
| 可解释 | 检索错了能一眼看出是哪个词命中/没命中；向量召回一个不相关片段时，很难解释为什么 |

**已知局限**：词面匹配可能遗漏换一种说法的问题。历史年休假分类分数为 0.56，但平均分不足以确认原因，需要逐题检查语料、来源、召回、生成与评分。向量检索是待验证方案；本公开仓库未包含 `w6_hr_qa/` 目录。

> 如果重做，我会做**混合检索**：BM25 保精度、向量补语义，用 RRF 融合两路排名，再加一层 cross-encoder 重排。理由见下方"已知限制"。

### 2. 为什么按标题切块，而不是定长切

制度文档是强结构的，条款边界就是语义边界。定长盲切会产生两种坏块：

- **标题空壳块**：一行短标题单独成块，占着召回名次但里面没有任何内容
- **跨条款块**：一个块横跨两个不相关的条款，召回回来一半是噪声

改成标题挂载之后，块数从早期的 323 降到 151（早期更完整的语料上），**块更少了但召回反而更好**——因为被砍掉的都是没有信息量的块。

320 字这个窗口是按条款平均长度试出来的：太小则一条条款被劈成两半、答案不完整；太大则一个块混多个主题、精度下降。60 字重叠是为了防止关键条件句正好被切在边界上——比如"满 1 年不满 10 年的，年休假 5 天"切在"年休假"前面，后半块就只剩"5 天"没有主语了。

### 3. 为什么强制"无依据即拒答"

对内部制度问答来说，**答错比不答危害大得多**。员工按错误的制度去办事，成本远高于让他去问 HR。

所以 system prompt 里写死了三条：只依据上下文、找不到就说"制度中未找到相关规定"、涉及数字必须与原文完全一致。`eval/questions.json` 里专门留了 4 道知识库中根本没有答案的题，用来测它会不会硬编。

## 一次值得记录的调试：0.025 这个假分数

第一次算出评测结果时，官方指标是 **0.025**——40 道题几乎全零。

历史调试记录将这一异常追溯到评分脚本；本节复述记录中的问题机制，不作为作者独立完成全部排查的证明。

**根因**：评价脚本里关键词匹配的正则写成了带捕获组的形式（`(\.\d+)?`）。Python 的 `re.findall` 在正则含捕获组时，**只返回捕获组的内容，不返回整个匹配**。于是 39 道题全被判成"一个字都没命中"，被一句 `if kws else 0.0` 直接打成 0 分。

唯一不是 0 的是那道具小数 `0.5` 的题——因为它命中了捕获组本身。所以均值正好是 `1/40 = 0.025`。

**修复**：把捕获组改成非捕获 `(?:\.\d+)?`，或改用 `re.finditer` 取 `group(0)`。同一批答案复算，真实命中率是 0.41（k=3）/ 0.47（k=6）。

**保存的回答不变，评分脚本修正后分数发生变化。**

沉淀成一句话：**先怀疑指标，再怀疑模型。**

大量零分而含小数的样例例外，是检查评分逻辑的线索；仅凭这种分布不能排除语料、检索或生成问题，需要用最小输入验证正则行为。

## 已知限制

1. **样本与语料有限**。当前语料为 2 份文档、52 个片段。历史 0.674 不能单独证明没有退化或具备泛化能力；判断退化需要一致的题集、评分定义和明确的比较基线。
2. **失败原因尚需逐题核查**。年休假历史分类分为 0.56。来源混淆与词面匹配不足是待验证假设，不能由该平均分直接断言。候选措施包括来源过滤、语义检索与重排，均需控制变量评估。
3. **20 题拒答集尚无固化的端到端结果**。`eval/questions.json` 包含 16 题可答、4 题不可答；题集与判据不等于实际运行结果。历史 31 题保存回答的分数也不等于这套 20 题的质量结论，完整历史回答与评测入口未包含在本公开仓库，不能承诺克隆后复现该分数。
4. **贡献与证据范围**。项目开发与整理使用 AI 辅助。仓库存在代码、提交或历史报告，不等于作者独立编写、本人复现或生产采用；具体贡献应按实际操作与验收记录说明。
